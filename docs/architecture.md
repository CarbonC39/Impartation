# 架构与功能边界

## 当前结构

这是一个 npm workspaces monorepo：

- `apps/frontend` 用 Vite 和 Phaser 3.90 呈现 Tiled 大厅、访客和聊天界面，并通过 `@colyseus/sdk` 连接服务。
- `apps/backend` 使用 Colyseus 0.18、`@colyseus/core`、WebSocket transport 和 tools 提供单个 `space` 房间。服务端校验访客加入、聊天和移动输入，按 50ms 步长执行移动与碰撞。移动位置和访客基础信息通过 Schema 同步；聊天通过房间消息广播。
- `packages/shared` 保存客户端与服务端共享的 schema、Zod 输入约束、房间/头像枚举和 Tiled 地图几何规则。
- `assets/maps` 提供地图与图块；后端启动时读取并验证 `.tmj` 文件。
- `better-sqlite3` 持有本地 SQLite 数据库。当前建有预留的 profiles 表，尚无已登录用户或账号流程。

客户端不负责决定最终位置或碰撞结果。未来的可编辑资源内容需要由对应后端服务验证与授权，不能仅把客户端状态当作持久化事实。

## 当前已做与预留

已做：开发访客昵称和三个占位头像、多人移动、文字聊天、20 秒自动重连、矩形碰撞、当前交互区提示及 SQLite 初始化。

地图预留 `media`、`whiteboard`、`board`、`pomodoro` 交互区类型和 `resourceId`。这些类型仅供地图识别和提示，影音同步、白板、留言板、番茄钟和换装均未实现。账号/登录明确留待用户后续提出。

## 后续同步功能建议

- **白板**：优先评估 Yjs 搭配 Excalidraw 的可行性。实现前确认各自许可、打包体积、持久化/房间同步模型以及能否嵌入 Phaser 场景；不要自行造 CRDT。
- **影音共享**：使用 HTMLMediaElement 或合适的现成播放器 SDK。服务端只同步经验证的播放/暂停、时间位置等控制状态；不要由服务端抓取用户给出的媒体 URL。需要明确平台播放策略、媒体来源许可和跨客户端同步体验。
- **留言板、番茄钟**：作为独立资源和服务端校验的房间功能设计，持久化业务数据与高频移动 Schema 分开。番茄钟的起止时间以服务端时钟为准。
- **账号**：按用户明确的后续需求接入经过维护的认证方案；不要把当前访客昵称或占位头像描述成身份认证。
- **语音**：目前没有语音功能，也未选定方案。将来如需语音，应单独评估 WebRTC/托管服务、隐私和运营成本，不通过 Colyseus 房间转发原始音频。

部署早期保持单后端实例和持久化卷。SQLite 文件不适合多实例共享；需要水平扩展时再设计 PostgreSQL、房间 Presence/Driver 和迁移方案。
