# 跨端访客身份方案草案

状态：讨论中，尚未实现跨端身份或修改数据库。工作分支仍为 `feat/account-system`，继承已有留言板和番茄钟。

## 已明确的范围

- 暂时不做正式账号系统，不实现注册、登录、密码管理或第三方账号绑定。
- “跨平台”指桌面、手机、网页共用同一身份，不指 GitHub、Discord 等外部账号关联。
- 用户自行用代理软件配置一组共用的 HTTP Basic Auth 凭据；项目不承担认证或代理配置，本轮不接入认证库。
- 暂不关注前端表现设计，先讨论跨端身份的数据与行为。

## 建议的最小实现（未落地）

使用独立于 Colyseus 房间 `sessionId` 的持久访客 ID。一个访客身份可以在多个客户端建立不同房间连接；断线、刷新或切换设备不必产生新的资料记录。资料仅包含展示昵称、现有占位头像等项目数据。

跨端关联可以先用可导入/导出的访客身份码：新设备导入同一个 ID，使用同一份资料。该方式仍是建议，尚未确定导入方式、资料读写规则或实现接口。无需为桌面、手机、网页分别创建绑定记录，也不把操作系统类型当成身份。

统一门禁不提供每个人独立的认证身份。当前建议的访客 ID 用来关联资料，不被描述为经过验证的用户身份，也不直接提升权限。项目不以客户端提交的 ID、昵称或平台名称授权留言删除；现有留言仍使用服务端连接会话判断作者。

## 与现有功能的接入点

- `profiles` 当前只是预留表。实现持久访客资料时需要版本化迁移，并明确资料 ID 与房间连接 ID 的区别。
- `SpaceRoom.onAuth` 当前只校验访客昵称和头像，不验证账号。后续跨端资料读取不应把客户端提交的访客 ID 当成认证结果。
- `board_notes.author_session_id` 与前端删除按钮目前都依赖当前房间会话；本阶段暂不改变这些权限语义。
- 旧留言不按昵称或新导入的访客 ID 自动认领。若以后希望跨设备管理自己的留言，再另行确定可信身份凭据。
- 好友、私密房间、设备管理、远程退出、管理后台不自动纳入本轮。

## 下一步讨论

先确定跨端身份如何携带：是否采用身份码导入/导出，以及昵称、头像是否由多个客户端共享修改。当前不讨论代理软件选择、Basic Auth 配置或正式认证库选型。

## 验收状态

本轮仅调整范围文档，未执行功能测试。跨端访客 ID、资料持久化、导入/导出和跨客户端行为均尚未实现，不能视为已验收。实现时应验证同一身份多连接、刷新后资料恢复、不同身份的资料区分、额外身份字段不能冒充当前留言作者，以及升级后保留原有数据。
